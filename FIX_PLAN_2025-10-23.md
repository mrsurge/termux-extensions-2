# Resolution Plan for file_editor_cm6 Stability Issues

**Date:** 2025-10-23

## 1. Overview

This document provides a deep explanation and a safe, strategic implementation plan to resolve a series of stability issues within the `file_editor_cm6` application. The primary symptom is a persistent `400 Bad Request` error that occurs during initial page load and subsequent file operations.

The investigation confirms that these errors are not random but stem from a few core architectural flaws. This plan will address them in a logical order to restore application stability.

## 2. Root Cause Analysis

All user-facing failures manifest as a `400 Bad Request`. This indicates the server is receiving the requests but considers them malformed or invalid. The causes are as follows:

### Cause A: Architectural Mismatch in Path Handling

This is the most significant issue. The backend was designed with a security-first approach, expecting **relative paths** for all file operations to prevent path traversal attacks. The frontend, however, was sending **absolute paths**. This fundamental disagreement in the API contract causes the server to reject the frontend's requests as invalid.

### Cause B: Asynchronous Race Condition on Initialization

On initial page load, the application attempts to open the last-used file. This action requires knowing the project root to calculate the file's relative path. However, this file-opening logic runs in parallel with the logic that determines the project root. The file operation often begins before the project root is known, causing it to send an invalid path to the backend and triggering a `400` error.

### Cause C: Incomplete UI Refactoring & Context-Unaware API Calls

The UI contains a disconnected, non-functional "Open Project" button in the main toolbar, which is a remnant of a past refactoring. Additionally, the JavaScript code for the file explorer uses relative URLs (e.g., `fetch('project/current')`) for API calls. Because the application serves all API endpoints under a specific prefix (`/api/app/file_editor_cm6/`), these calls are sent to an invalid endpoint, which the server also rejects with a `400` error.

## 3. Implementation Plan

This plan is ordered to be as safe and non-disruptive as possible. It resolves dependencies at each stage before moving to the next, starting with the UI and finishing with the core application logic.

### **Step 2: Enforce a Sequential Boot Process**

**Goal:** Directly fix the `400 Bad Request` error that occurs on initial page load by eliminating the race condition.

**File to Modify:** `app/apps/file_editor_cm6/main.js`

**Explanation:** The current startup logic runs initialization tasks in parallel. We must enforce a strict sequence: first, initialize the UI and get the project context, and *then* attempt to open any files.

**Action:**
Go to the end of the file. Find the block of code that performs the initial setup and file loading.

**Replace this code:**
```javascript
// (Representative "Before" Code)
// Initialize explorer
initExplorerUI().catch(e => {
  console.error('Failed to initialize explorer UI:', e);
});

// Open file via URL param or saved state
const params = new URLSearchParams(window.location.search);
const fileFromUrl = params.get('file');
if (fileFromUrl) {
  // ... logic to open file
} else if (state.lastPath) {
  // ... logic to open file
}

// Save state on exit
host.onBeforeExit(() => {
  // ...
});
```

**With this new code:**
```javascript
// (New Code)
async function main() {
  // Initialize explorer first to get project context
  await initExplorerUI().catch(e => {
    console.error('Failed to initialize explorer UI:', e);
  });

  // Ensure we have the project root before opening any files
  await getCurrentProjectRoot();

  // Open file via URL param or saved state
  const params = new URLSearchParams(window.location.search);
  const fileFromUrl = params.get('file');
  if (fileFromUrl) {
    const abs = toAbsolute(fileFromUrl, null, HOME_DIR);
    lastPickerPath = parentDir(abs);
    openFile(abs).catch((e) => {
      host.toast(`Failed to open file: ${e.message}`);
      currentPath = ''; currentPathExists = false; setText(''); markUnsaved(false); updatePathDisplay();
    });
  } else if (state.draft) {
    currentPath = state.lastPath ? toAbsolute(state.lastPath, null, HOME_DIR) : '';
    currentPathExists = false;
    currentModeLanguage = currentPath ? detectLanguageFromFilename(currentPath) : null;
  } else if (state.lastPath) {
    const abs = toAbsolute(state.lastPath, null, HOME_DIR);
    lastPickerPath = parentDir(abs);
    openFile(abs).catch(() => {
      currentPath = abs; currentPathExists = false; setText(''); updatePathDisplay();
    });
  }
}

// Run the main boot sequence
main();

// Save state on exit
host.onBeforeExit(() => {
  if (unsaved) { showConfirm(); host.toast('Unsaved changes — Save or Discard before leaving.'); return { cancel:true }; }
  return {
    lastPath: currentPath || null,
    draft: unsaved ? getText() : null,
    showLineNumbers, showLineShading,
    showSyntaxHighlight, wordWrap,
    autoSaveEnabled, theme: currentTheme,
  };
});
```

### **Step 3: Implement Frontend-Side Relative Path Handling**

**Goal:** Fix the core architectural flaw causing `400` errors during all file operations (saving, opening).

**File to Modify:** `app/apps/file_editor_cm6/main.js`

**Explanation:** The frontend must be modified to send relative paths to the backend, conforming to its API contract. This involves calculating the relative path from the absolute path before making the API call.

**Action:**

1.  **Modify `openWebSocket()` function:**

    **Replace this:**
    ```javascript
    // (Representative "Before" Code)
    const wsUrl = `${protocol}//${window.location.host}/api/app/file_editor_cm6/ws/read?path=${encodeURIComponent(path)}&client_id=${encodeURIComponent(clientId)}`;
    ```

    **With this:**
    ```javascript
    // (New Code)
    const projectRoot = await getCurrentProjectRoot();
    let relPath = path; // Assume path is already relative if projectRoot is not set or path is not absolute
    if (projectRoot && path.startsWith(projectRoot)) {
      relPath = path.substring(projectRoot.length);
      if (relPath.startsWith('/')) relPath = relPath.substring(1);
    }

    const protocol = window.location.protocol === 'https:' ? 'wss:' : 'ws:';
    const wsUrl = `${protocol}//${window.location.host}/api/app/file_editor_cm6/ws/read?path=${encodeURIComponent(relPath)}&client_id=${encodeURIComponent(clientId)}`;
    ```

2.  **Modify `doSave()` function:**

    **Replace this:**
    ```javascript
    // (Representative "Before" Code)
    const payload = {
      path: targetPath,
      content: content,
      client_id: clientId,
      op_id: opId
    };
    ```

    **With this:**
    ```javascript
    // (New Code)
    const projectRoot = await getCurrentProjectRoot();
    let relTargetPath = targetPath; // Assume path is already relative if projectRoot is not set or path is not absolute
    if (projectRoot && targetPath.startsWith(projectRoot)) {
      relTargetPath = targetPath.substring(projectRoot.length);
      if (relTargetPath.startsWith('/')) relTargetPath = relTargetPath.substring(1);
    }

    const payload = {
      path: relTargetPath,
      content: content,
      client_id: clientId,
      op_id: opId
    };
    ```

### **Step 4: Correct API Endpoint Paths in Explorer**

**Goal:** Fix the final source of `400` errors that occur when using the file explorer and project features.

**File to Modify:** `app/apps/file_editor_cm6/static/js/explorer.js`

**Explanation:** The `fetch` calls in this file use relative URLs, which the server rejects. They must be updated to use the full, correct API path.

**Action:**
Perform a search-and-replace within the file for all occurrences of `fetch` that use a relative path.

**Example:**

**Replace this:**
```javascript
// (Representative "Before" Code)
const r = await fetch('project/current');
```

**With this:**
```javascript
// (New Code)
const r = await fetch('/api/app/file_editor_cm6/project/current');
```

Apply this correction to all `fetch` calls in the file, including those for `/project/open`, `/history/files`, `/history/file`, and `/explorer/list`.
