# Backend-Centric Agent Drawer Refactor Plan

**Objective:** Move 100% of agent session ownership (message storage, transcript assembly, history restoration) into the Python backend so the browser acts purely as a rendering client.

---

## 1. Guiding Principles

1. **Python owns state.** All agent transcripts, pending messages, session metadata, and restore logic live in backend data structures persisted to disk.
2. **Browser renders.** The frontend only submits user prompts / UI intents and renders whatever snapshot the backend returns—no mutation of session data client-side.
3. **Deterministic flows.** WebSocket payloads become render-ready messages (full transcript or incremental patches) generated by the server.
4. **Single source of truth.** The existing `~/.codex/app_prefs/code_cm6.json` (or successor) remains the authoritative on-disk store; the UI never persists sessions directly.

---

## 2. Backend Workstreams

### 2.1 Session Storage Overhaul
- **Files:** `app/apps/file_editor_cm6/agent_session_store.py`, `agent_ws.py`
- **Tasks:**
  - Add helpers for incrementally appending messages (user, system, token, final) directly on receipt.
  - Maintain “pending assistant” entries on the backend; update text per token and mark complete on `final` events.
  - Introduce locking/queuing to keep per-session message order deterministic.
  - Ensure updates flush immediately to disk (or at least buffered with safe flush) to survive crashes.

### 2.2 WebSocket Response Restructuring
- **Files:** `agent_ws.py`
- **Tasks:**
  - For every agent event, persist, then broadcast a render payload: either
    - a full transcript snapshot, or
    - a minimal diff ({ type: 'token', messageId, delta }) that the frontend can apply without storing state.
  - Include `session` in every payload so the UI routes to the correct transcript.
  - Remove expectations that the client will echo session mutations back.

### 2.3 REST API Additions
- **Files:** `agent_routes.py`, possibly new `session_routes.py`
- **Tasks:**
  - `GET /api/app/file_editor_cm6/agent/session/<id>` → full persisted transcript & metadata (used on initial load).
  - `GET /api/app/file_editor_cm6/agent/sessions` → summary list for session picker.
  - `POST /api/app/file_editor_cm6/agent/session/<id>/message` → enqueue user prompt; WS handles output.
  - Optional `POST /session/<id>/rename`, `DELETE /session/<id>` to keep UI simple.

### 2.4 Adapter Hooks
- **Files:** `agent_bridge.py`
- **Tasks:**
  - Emit structured callbacks to `agent_session_store` whenever Codex/Gemini events arrive (token, system, final, error).
  - Guarantee conversation ID updates and restore decisions stay backend-only.

### 2.5 Persistence Format Review
- **Files:** `agent_session_store.py`
- **Tasks:**
  - Evaluate whether current JSON structure suits streaming updates; adjust schema if necessary (e.g., add `pending_message_id`).
  - Keep compatibility with existing data or add migration routine.

---

## 3. Frontend Simplification

### 3.1 Session Handling Removal
- **Files:** `app/apps/file_editor_cm6/static/js/agent_drawer.js`
- **Tasks:**
  - Delete local session mutation logic (`sessions` object becomes read-only cache).
  - Remove `saveSessionsToDisk()` and related preference writes.
  - Replace `handleAgentMessage` with rendering logic that consumes backend snapshots.

### 3.2 New Data Flow
- **Files:** `agent_drawer.js`, `static/js/main.js`
- **Tasks:**
  - On drawer open: `fetch(/agent/sessions)` → populate list.
  - On session switch: `fetch(/agent/session/<id>)` → render transcript.
  - WebSocket handler simply applies backend-provided updates (e.g., append bubble, update status) without persisting.

### 3.3 UI Adjustments
- Ensure message bubbles, stats, and shell indicators respond to backend events (may need new event types for snapshot vs incremental update).

---

## 4. Retained Logic

- Shared-shell management (spawn, reuse, label discovery) remains in `agent_ws.py` / `agent_bridge.py`.
- History restoration logic (needs_restore calculation, transcript prepending) stays backend-side—just triggered earlier in the pipeline.
- Approval policy, sandbox selection, and Codex/Gemini protocol adapters are largely untouched aside from persistence hooks.
- Terminal editor integration, diff tracking, and other non-agent features unaffected.

---

## 5. Deletions / Cleanup

- Frontend debounced saving, local session map updates, and preference persistence for transcripts.
- Redundant `buildHistoryContext` helper in JS once the backend provides fully-prepped transcripts.
- Any JS-level conflict handling for session state.

---

## 6. Testing Strategy

1. **Unit Tests (Python):**
   - Ensure token → pending update → final message transitions produce expected disk records.
   - Validate history replay pipeline using stored transcripts.
2. **Integration Tests:**
   - Simulate Codex event stream, confirm resulting WS payloads and disk output.
   - Browser-level smoke test: refresh during streaming response, verify transcript complete on reload.
3. **Manual QA:**
   - Resuming sessions after framework restart, verifying `conversationId` continuity.
   - Switching between multiple sessions mid-stream.

## 8. Open Questions

1. Snapshot vs incremental WS payloads: prefer full snapshot for simplicity or diffs for bandwidth?
2. Need new persistence schema (e.g., SQLite) or stick with JSON files?
3. Should we emit version numbers with transcripts to prevent stale overwrites on the client?

Resolve these before implementation to avoid churn.
