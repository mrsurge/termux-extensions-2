## FWS structured log inspection
- Fact: Framework-shell log inspection must stay generic and event-first. Do not overfit the tool contract to `codex-app-server` or any other single producer. JSON-RPC is an important parser lane, but not the semantic model.
- Fact: The preferred design lives in `docs/planning/FWS_STRUCTURED_LOG_INSPECTION.md`, with current implementation follow-ups in `docs/planning/FWS_STRUCTURED_LOG_INSPECTION_SUPPLEMENT.md`. - Fact: The current TE2-side implementation of `te2_fws_log_inspect` now promotes stable prefixed plain events into signatures such as `plain:ipc_chunk` and supports minimal exclusions through `exclude_query` and `exclude_signature`. Query mode still uses `search_logs()` semantics.
- Fact: Long-line inspection is intended to replace much of the ad hoc Python-heredoc log workflow. The upstream target for a mature version is `framework-shells` itself via a native structured `inspect_logs(...)` API with parser lanes, signature aggregation, and structured path/value filtering.

## shellspec role and terminal broker progression
- Fact: In this repo, shellspecs are iterative-development scaffolding, not an end-user surface. For prototype work such as `terminal_testing`, it is acceptable for a shellspec to launch a temporary broker command while validating a transport design.
- Fact: The current preferred terminal-stream progression is: prototype as a shellspec-launched broker running under an FWS `pipe` shell, then productize by moving the broker behavior into native FWS code with a distinct backend or engine name such as `terminal_stream` rather than overloading raw `pipe`.
- Fact: The reason for that progression is to validate framing, replay, hydration, and input-latency behavior quickly in userland first, then move PTY lifecycle, framing, resize, replay contract, and sequencing into native FWS machinery where the hot path can live in machine code.
- Fact: The current `terminal_testing` prototype direction is locked to a Node broker with an app-local PTY dependency, specifically `node-pty` unless a concrete incompatibility blocks it.
- Fact: The new `terminal_testing` frontend is intended to be type-safe and minified through an app-local TypeScript plus esbuild build that emits a bundled `static/dist` frontend script rather than serving a raw source `main.js` file.
- Fact: The current preferred `terminal_testing` protocol split is: JSON-RPC 2.0 notifications for broker stdin and client-originated control/input such as `terminal.connect`, `terminal.input`, `terminal.resize`, `terminal.destroy`, and `terminal.ping`; JSONL event objects remain the stdout and replay contract for output events such as `hello`, `data`, `closed`, `error`, and `pong`.
- Citations: `docs/planning/TERMINAL_INPUT_LATENCY_PATCH_PLAN.md`, agent log `#184`, user instruction

## terminal touch wheel scrolling
- Fact: Both `app/apps/terminal` and the `file_editor_cm6` terminal drawer now use the vendored `touch_to_mouse_handler.js` helper to split touch gestures into three paths: tap passthrough, long-press synthetic mouse selection, and drag-driven synthetic `wheel` events aimed at the xterm viewport/root instead of the touched character cell.
