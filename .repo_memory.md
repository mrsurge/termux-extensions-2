## App Framework

- Fact: `/api/apps` is served from the in-memory apps registry snapshot. Manifest metadata changes, including `entrypoints.frontend_script` query bumps, need `/api/apps/reload` to refresh the registry without restarting the framework.
- Fact: App-shell quit actions should use `/api/apps/{app_id}/quit`, which delegates through app runtime shutdown and framework-shell app-group shutdown.
- Fact: App manifests can declare `sidebar_state`; the app catalog preserves that capability and app lifecycle stores semantic readiness separately from shell/TCP readiness.
- Fact: App/backend readiness is opt-in through top-level manifest field `readiness_support: true`. Apps without that flag default to unsupported: the app readiness endpoints are unavailable for them, lifecycle registration does not synthesize `starting`, and the framework `/app/{app_id}` shell bypasses the backend-readiness placeholder/wait path. All real builtin apps under `app/apps/*` declare support; generated/user-local wrappers must opt in explicitly.
- Fact: Semantic app/backend readiness for supported apps is posted or put to `POST /api/apps/{app_id}/readiness` or `PUT /api/apps/{app_id}/readiness` with minimum body `{"status":"ready"}` and can be read back with `GET /api/apps/{app_id}/readiness`. It is app lifecycle state keyed by `app_id`; it must not require or store `host_id`, `token_id`, `url`, conversation id, or sidebar restore state.
- Fact: Supported app worker start/register puts app lifecycle readiness into `starting` without blocking on shellspec readiness probe timeouts, but must preserve an already-posted `ready` state if the backend wins the startup race. The framework `/app/{app_id}` shell owns the backend-readiness placeholder and waits without a fixed timeout until the supported app backend posts app-level readiness.
- Fact: The app lifecycle event contract is shared by the legacy Python framework and the Rust spike. `/ws/apps` emits an initial `apps_snapshot` and live app state updates; `/api/apps/events` SSE also emits an initial `apps_snapshot`, registry/readiness events, `catalog_snapshot`, and shell/FWS-derived `app_running_changed` deltas. App shell readiness should consume those event streams instead of long polling readiness.
- Fact: Normal framework apps become app/backend-ready when their backend module is imported, routes are mounted, lifespans are active, and the backend can accept app API requests. The standard `app.libs.app_worker` path posts readiness at that backend-serving point unless an app provides its own backend-serving hook. Proxy/shim apps become ready when the backend/upstream that owns their frontend is actually serving that frontend/content and must publish the same readiness endpoint from that serving point.
- Fact: `app/apps/als_rs` is the tracked builtin ALS-RS proxy-shell wrapper. Its manifest identity is `id: "als-rs"`, while the builtin directory name is `als_rs`.

## Stateful Sidebar App Windows

- Fact: `/sidebar_ipc` owns the typed sidebar window ledger persisted in UI preference `sidebarWindowState`. The ledger stores app/window metadata, the current live same-origin `url`, restore URL/query-state, TE2 host/token/console ids, readiness, and optional state-kind metadata. App-specific query data such as `path` is stored only as app-owned opaque `query_state`; the sidebar host must not reinterpret it as host-owned navigation state.
- Fact: Current window/app methods include `sidebar.launcher.catalog.get`, `sidebar.windows.list`, `sidebar.window.create`, `sidebar.window.openUrl`, `sidebar.window.state.update`, `sidebar.window.activate`, `sidebar.window.close`, and `sidebar.window.readiness.update`. - Fact: Stateful app backends can receive focused-window notifications by keeping a persistent `/sidebar_ipc` connection and registering with `app`, `app_id`, or `appId`.
