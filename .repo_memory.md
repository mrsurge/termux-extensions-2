## FWS structured log inspection
- Fact: Framework-shell log inspection must stay generic and event-first. Do not overfit the tool contract to `codex-app-server` or any other single producer. JSON-RPC is an important parser lane, but not the semantic model.
- Fact: The preferred design lives in `docs/planning/FWS_STRUCTURED_LOG_INSPECTION.md`, with current implementation follow-ups in `docs/planning/FWS_STRUCTURED_LOG_INSPECTION_SUPPLEMENT.md`. The inspection surface should annotate one raw log event with parsed fragments, detected formats, and generic event signatures rather than baking in app-specific concepts like `userMessage` or `agentMessage`.
- Fact: The current TE2-side implementation of `te2_fws_log_inspect` now promotes stable prefixed plain events into signatures such as `plain:ipc_chunk` and supports minimal exclusions through `exclude_query` and `exclude_signature`. This makes `summary.signature_counts` and `summary.top_signatures` directly useful for noisy mixed-format shells like the workbench adapter.
- Fact: The TE2-side tail path for `te2_fws_log_inspect` now consumes framework-shell event windows directly instead of rebuilding records only from `get_log_tail()` line text. Tail results therefore preserve `byte_window_start`, `byte_window_end`, stream-level `partial_head`, and per-record `byte_start`, `byte_end`, `partial_head`, and `partial_tail`, so clipped first-tail records are explicitly marked instead of silently appearing as clean events. Query mode still uses `search_logs()` semantics.
- Fact: Long-line inspection is intended to replace much of the ad hoc Python-heredoc log workflow. The upstream target for a mature version is `framework-shells` itself via a native structured `inspect_logs(...)` API with parser lanes, signature aggregation, and structured path/value filtering.

## shellspec role and terminal broker progression
- Fact: In this repo, shellspecs are iterative-development scaffolding, not an end-user surface. For prototype work such as `terminal_testing`, it is acceptable for a shellspec to launch a temporary broker command while validating a transport design.
- Fact: The current preferred terminal-stream progression is: prototype as a shellspec-launched broker running under an FWS `pipe` shell, then productize by moving the broker behavior into native FWS code with a distinct backend or engine name such as `terminal_stream` rather than overloading raw `pipe`.
- Fact: The reason for that progression is to validate framing, replay, hydration, and input-latency behavior quickly in userland first, then move PTY lifecycle, framing, resize, replay contract, and sequencing into native FWS machinery where the hot path can live in machine code.
